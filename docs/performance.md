# Performance

**English** · [简体中文](performance.zh-CN.md)

[Documentation index](../README.md#documentation) · [Deployment](deployment.md) · [Design review](design-review.md)

Decis runs decision models — a single forward pass per request, no text generation — so the
numbers that matter are per-question latency, cold-start time, and memory. This page
collects every measured figure the project quotes. Nothing here is hand-written: each table
is rendered by [`benchmarks/report.py`](../benchmarks/report.py) from the raw JSON in
[`benchmarks/results/`](../benchmarks/results/), and CI fails if a checked-in table no
longer matches that data.

Measurements were taken on a **24 vCPU aarch64 host with no GPU**. Decision models are also
fast on Apple silicon with MLX — upstream publishes figures for that setup that are far
lower — but that is not what a CPU-only container does.

## Latency

<!-- LATENCY:START -->

| Engine | Device | dtype | Threads | 1 question | 10 questions | Cold start | Peak RSS |
|---|---|---|---:|---:|---:|---:|---:|
| `laya` | cpu | float32 | 24 | 446 ms | 3,222 ms (322.1 ms/question) | 76.3 s | 2.8 GB |
| `laya-multilingual` | cpu | float32 | 24 | 231 ms | 987 ms (98.7 ms/question) | 72.9 s | 4.84 GB |

Generated by [`benchmarks/report.py`](../benchmarks/report.py) from the raw JSON in [`benchmarks/results/`](../benchmarks/results/); a whole row comes from one configuration (the thread count torch picks by default, one per vCPU). p50 over the recorded samples, single process, within-request batching only.

**These are latencies, not throughput.** Every question in a row shares one `state`, which is the easy case. Cross-request batching has since been measured and does **not** raise throughput on CPU -- see the cross-request batching section below and [`docs/design-review.md §4-M5`](design-review.md).

<!-- LATENCY:END -->

The latency table is an easy case on purpose: all questions in one request share a single
`state`. The two things worth reading from it:

- Asking ten questions in one call costs much less per question than asking one.
- Cold start is about 75 seconds — 73 s to 76 s in the column above — and peak memory is
  several times the size of the weight files. Size the readiness probe and the container
  memory limit from this table, not from the download size.

## dtype, per engine and device

`kev-0.8b`'s Qwen3.5 backbone needs `flash-linear-attention` and `causal_conv1d`, both of
which require Triton/CUDA. On CPU it is an order of magnitude slower than Laya, and its
`bf16` path is worse still:

<!-- DTYPE:START -->

| Engine | dtype | 3 questions | relative | vs. baseline |
|---|---|---:|---:|---|
| `kev-0.8b` | `fp32` | 1,656 ms | 1x | baseline |
| `kev-0.8b` | `bf16` | 137,174 ms | 83x | same argmax, max probability delta 0.01 |

Generated by [`benchmarks/report.py`](../benchmarks/report.py). One observation per dtype, so the ratio is an order-of-magnitude finding, not a statistic, and the comparison column is computed from the recorded answer bodies rather than from the prose next to them.

<!-- DTYPE:END -->

That is why Decis picks a dtype per engine *and* device
([`engines/registry.py`](../src/decis/engines/registry.py)) and warns when a configuration
is known to be bad, rather than silently choosing it.

## Cross-request batching: measured, and the answer is no

Joining questions from *different* requests into one forward pass was the design's
throughput claim. It has been measured, and the result is negative:

<!-- BATCHING:START -->

| Item set | Sequence length | padding | Best batch | vs. serial |
|---|---|---:|---:|---:|
| one state (positive control, short) | 115–115 | 1.00 | 8 | 1.92x |
| one state (positive control) | 393–393 | 1.00 | 16 | 1.24x |
| different states, similar lengths | 530–674 | 1.10 | 8 | 1.09x |
| different states, skewed lengths | 140–821 | 2.41 | 8 | 0.34x |

The positive control (identical items, padding 1.00) reaches **1.92x** (`shared_short`, batch 8), which confirms the bottleneck is per-call fixed overhead and that this harness can detect a gain. For the shape real traffic has -- different states -- the best case is 1.09x (`uniform`, batch 8) and the worst is 0.34x (`skewed`, batch 8). When lengths are skewed, padding reaches 2.47x (`skewed`, batch 16): every row is padded to the longest in its batch, and that wasted compute shows up directly as a higher per-item cost.

Raw JSON in [`benchmarks/results/`](../benchmarks/results/); the full table -- every batch size, padding, break-even wait, process comparison -- is in [`docs/design-review.md §4-M5`](design-review.md). Batches are synthesised by calling the engine directly, with no queue and no cancellation, so these are an **upper bound** on a real batcher.

<!-- BATCHING:END -->

The full table — every batch size, padding ratio, break-even wait, and the multiprocess
comparison — is in [`design-review.md §4-M5`](design-review.md). Cross-request batching
only pays when sequences are short enough that per-call overhead dominates; at realistic
state lengths there is nothing left to amortise, and once lengths vary, padding makes it
several times slower. `decis.batch_size` is still reported on every response, because a
mechanism that cannot be observed cannot be tested.

## Reproducing these numbers

```bash
uv run decis bench --engine laya-multilingual --batch 1,3,10,30   # collect
uv run python benchmarks/report.py --write                        # render
uv run python benchmarks/report.py --check                        # what CI runs
```

Methodology, host specification, and the known limitations of each dataset are in
[`benchmarks/README.md`](../benchmarks/README.md). Do not quote a figure that is not in
`benchmarks/results/`; see [`AGENTS.md §8`](../AGENTS.md).
